# ADR-0003 A command line that does not depend on Node

- Status: accepted (2026-10-17)
- Related: ADR-0005 (write protocol)

## Context
After an agent finishes a note, it runs a command to write the status back (`resolve` / `wontfix`). Currently `pizhu.cmd` in the data folder is `node "<development folder>\packages\cli\dist\index.js" ...`:
it requires Node on the user's machine, and the path points into the development folder — **it does not work at all once installed on someone else's computer**. In addition:
- The REVIEW.md generated by the command line differs from the one generated by the UI (the command line does not pass options such as `includeResolved`), so one write-back turns the UI's version back into the default layout.
- The command line overwrites the whole file non-atomically, so it and the UI can clobber each other (see ADR-0005).
- `--version` is hard-coded to `0.1.0`.

## Decision
1. **A new shared C# library `<Name>.Core`** (`net10.0`, no WPF dependency, can be built on a Mac): reads and writes notes files, the write protocol (ADR-0005), REVIEW.md generation, category and position text.
   The shell and the command line both use it.
2. **The command line becomes a standalone C# + NativeAOT program** `<name>-cli.exe`: a few MB, millisecond startup (agents call it often), and no runtime for users to install.
   `bin\<name>.cmd` in the install folder forwards to it, and the installer adds it to PATH (optional).
3. **Commands and arguments stay the same**: `list`, `review`, `resolve <id> -m`, `wontfix <id> -m`, `--root`, `--all`, `--json`, `--author`.
   Exit codes: 0 success, 1 runtime error, 2 usage error, 3 note not found; the `--json` output is stable and documented; `--version` follows the product version.
4. The write-back script `.<name>/<name>.cmd` in the data folder calls `<name>-cli.exe` in the install folder (absolute path, refreshed every time the app starts; if the app is moved, the next launch fixes it).
5. **The TS `packages/core` stays for the UI** (text copied for AI, descriptions in the UI); REVIEW.md is generated only by C#.
   Text that both TS and C# produce (position descriptions, category names, ...) **runs against the same golden files**: `tests/golden/<scenario>.<lang>.{json,md}`; it passes only if both sides match character for character.
6. The Node `packages/cli` is retired (deleted once the golden tests pass and the new command line is installed).

## Rejected alternatives
- **Jint (running JS inside .NET) to call the TS core**: core is only about 460 lines, not worth embedding a JS engine; Jint has no `Intl`, so multilingual support would need shims; startup is slow and AOT is hard.
- **Node single-executable (SEA) / Bun compile**: each is hundreds of MB, just to run a few hundred lines of logic.
- **Make the GUI program double as the command line**: a WinExe has no standard output in a terminal, and the `AttachConsole` approach behaves differently across terminals.
- **Command line edits only the JSON and leaves REVIEW.md to be regenerated the next time the UI opens**: while the UI is closed REVIEW.md is stale, so the agent reads the wrong state.

## Consequences
- The REVIEW.md generation logic moves from TS to C#. First convert the existing REVIEW.md-related cases in `packages/core/test` into golden files, then port, so the output stays identical.
- When the shell writes a note, C# generates REVIEW.md, and the web UI no longer sends the whole REVIEW.md text across the bridge (which also saves one large string transfer).
- For a future Mac version: `<Name>.Core` and the command line build directly for `osx-arm64`.
