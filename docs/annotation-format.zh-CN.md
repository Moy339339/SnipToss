# 批注数据格式 `sniptoss/5`（超级批注）

本文是 [annotation-format.md](annotation-format.md) 的中文版；两者不一致时以英文版为准。

这份文档是**给 agent 的契约**：批注工具写什么、agent 读什么，都以这里为准。
旧程序会读错的改动（删字段、改含义、改单位）才升主版本号；只加可选字段不升，文档里写明从哪版起有。新程序始终能读以前各版本的文件。

**JSON Schema**：`docs/schema/sniptoss-5.schema.json`（JSON Schema 2020-12），写自己的脚本、插件时可以拿它校验。
它管的是「程序写出来的文件长什么样」（每个字段都带着）；读的时候更宽松，见下面「读取规则」。
Schema 表达不了的一条：同一个文件里批注的 `id` 不能重复。

版本：

| 版本 | 变化 |
|---|---|
| `sniptoss/5`（2026-10-25） | **一条批注可以标几处**：`anchor.shape`（一个形状）改成 `anchor.shapes`（数组，一处或几处，这条意见对每一处都适用）。旧版本读进来时 `shape` 换成只有一项的 `shapes`，写回时就是 `sniptoss/5`。旧程序读不懂（会当成没有位置），所以升主版本号 |
| `sniptoss/4`（2026-10-17） | 改名（内容和 `pizhu/3` 完全一样）：数据目录 `.pizhu/` 改叫 `.sniptoss/`，回写命令 `pizhu` 改叫 `sniptoss`。见文末「从 pizhu 迁移」 |
| `pizhu/3`（2026-10-17） | 新增**整个文件夹的意见**：`material.kind` 可以是 `folder`，一个文件夹一个批注文件（文件名见下），管文件夹里的所有素材（含子文件夹） |
| `pizhu/2`（2026-10-15） | 手绘 `path` 加可选的 `breaks`：一笔划出画面又回来时，只记画面里的几段，段与段之间不连线 |
| `pizhu/1` | 最初版本。新版本的子集，照常能读；程序改动过的文件写回时变成当前版本 |

只加可选内容的不升版本号，从 1.0.0 起写明是程序哪一版加的。本文写到的 1.0.0 都已经有，包括可选的 `project.json`（REVIEW.md 的语言）、单条批注的 `material_sha256`（写在素材哪一版上）、单条批注的 `color`（标记单独换的颜色）、`anchor.shapes` 每一处的 `color`（几处分别换的颜色）。

## 放在哪

批注跟着素材走，放在素材所在项目根目录下的 `.sniptoss/`（像 `.git/` 一样）：

```
<素材项目>/
  .sniptoss/
    REVIEW.md                      # 自动生成：所有未处理批注的汇总，agent 首先读这个
    project.json                   # 这个批注目录的设置：REVIEW.md 用哪种语言写（见下文「目录设置」）
    annotations/
      assets__hero.png.json        # 一个素材一个文件；文件名 = 相对路径里的 / 换成 __
      video__intro.mp4.json
      @folder.json                 # 整个文件夹的意见（pizhu/3 起）：放 .sniptoss 的这个文件夹本身
      assets__ui@folder.json       #   子文件夹 assets/ui；素材总有扩展名（.png.json），撞不上
    snapshots/
      k3f9a2.png                   # 每条批注一张截图：框出位置的原图 / 视频那一帧 / PDF 那一页
    .gitignore                     # 只忽略写入时的临时文件（*.tmp）和锁（*.lock）；程序写过东西、没有这个文件时放一份，有了不动
```

批注本身要不要提交进 git 由用户决定，程序不替他忽略。

- 路径一律用**相对 `.sniptoss/` 所在目录**的正斜杠路径，如 `assets/hero.png`。
- `REVIEW.md` 和 `snapshots/` 都可以从 `annotations/*.json` 重新生成，**真实数据只在 JSON 里**。
- **文件名只是个方便人看的名字，是哪份素材以文件里的 `material.path` 为准**；读的时候不要从文件名反推路径。
  文件名超过 200 个字符的（素材在项目里藏得深）：只留结尾 120 个字符，后面接 `~` 和整个路径的指纹（FNV-1a 64 位，16 位十六进制），
  如 `…__第8层__最终稿.png~1f3a9c0b7d2e4f68.json`（NTFS 一级名字最多 255 个字符）。规则在 core 的 `slugFor`。
- 文件名可能撞：项目根下的 `a__b.png` 和 `a/b.png` 都叫 `a__b.png.json`。程序遇到「这个名字已经是另一份素材的」就不写、提示改名，
  不会把两份的批注合进一个文件。

## 目录设置 `project.json`（可选）

```json
{
  "language": "zh-CN"
}
```

- `language`：`REVIEW.md` 用哪种语言写（语言代码：`zh-CN`、`zh-TW`、`en`、`ja`、`ko`、`fr`、`de`、`es`、`it`、`pt-BR`、`ru`）。程序写的 `REVIEW.md` 和命令行 `sniptoss review` 都照它。
- 程序第一次要写 `REVIEW.md`、这个文件还没有时放一份：目录里**已经有** `REVIEW.md`（以前的版本写的，都是中文）就记 `zh-CN`；没有就记当时的界面语言（命令行：系统的显示语言）。
- 之后**不跟界面语言变**：几个人用不同语言在同一个项目里写批注，`REVIEW.md` 不会被来回改写（docs/adr/0001-i18n.md 第 7 条）。想换语言就手改这个文件：命令行下次就照它写；程序重新打开后、下次写 `REVIEW.md` 时生效。
- 读的时候：文件没有、不是合法的 JSON、`language` 不认识，都按上一条的规则重新定（不认识的不覆盖，原样留着）。以后可能往里加别的字段，读的程序不认识的字段不管。
- 「复制成文字」交出去的那段话不看它，跟界面语言（是当下那个人交给自己的 AI 的）。

## 素材文件 `annotations/<slug>.json`

```jsonc
{
  "schema": "sniptoss/5",
  "material": {
    "path": "assets/hero.png",          // 相对路径
    "kind": "image",                    // image | video | pdf | slides
    "sha256": "9f2c…",                  // 写第一条批注时素材的 SHA-256；每条批注自己也记（material_sha256），以每条的为准
    "width": 1920, "height": 1080,      // 图片/视频的像素尺寸；pdf/slides 不写，见每页
    "duration": 63.2,                   // 仅视频：秒
    "pages": [{ "width": 960, "height": 540 }]  // 仅 pdf/slides：每页尺寸（PDF 点 / 幻灯片像素）
  },
  "annotations": [ /* 见下 */ ]
}
```

几种图片的 `width` / `height` 怎么来：

- **SVG**：它自己写的 `width` / `height`（单位换算成像素）；没写的按 `viewBox` 的宽高。乘回去就是 SVG 里的坐标（`viewBox` 不从 0 开始时再加上它的起点）
- **TIFF、HEIC / HEIF**：按文件记的方向转正之后的像素尺寸；多页的 TIFF 指第一页

### 整个文件夹的意见（`pizhu/3` 起）

不针对某一个文件、而是对一整个文件夹说的话（「这一批整体偏暗，全部提亮」）。**管这个文件夹里的所有素材，含子文件夹。**

```jsonc
{
  "schema": "sniptoss/5",
  "material": {
    "path": "assets/ui",                // 文件夹的相对路径；"." = 放 .sniptoss 的这个文件夹本身
    "kind": "folder"                    // 没有 sha256、尺寸
  },
  "annotations": [ /* 同下，anchor 是空对象 {}，没有截图 */ ]
}
```

## 单条批注

```jsonc
{
  "id": "k3f9a2",                       // 6 位小写字母数字；超级批注新建时避开已有的，项目内不重复（读的时候只保证同一个文件里不重复）；agent 引用批注时用它
  "status": "open",                     // open 待处理 | resolved 已改 | wontfix 不改
  "category": "change",                 // change 修改 | remove 删除 | add 新增 | question 疑问
  "body": "标题字太细了，换成粗一点的黑体",
  "anchor": {
    "page": 3,                          // 仅 pdf/slides：第几页，从 1 开始
    "time": { "start": 12.5, "end": 15.0 },  // 仅视频：秒；只标一个时刻时 end 省略
    "shapes": [                         // 这条意见标在哪几处（sniptoss/5 起；一处也是数组）。坐标全部归一化到 0–1，原点在左上角
      { "type": "rect", "x": 0.12, "y": 0.08, "w": 0.40, "h": 0.10 },
      { "type": "rect", "x": 0.12, "y": 0.62, "w": 0.40, "h": 0.10 }
      // 其他形状：
      // { "type": "point", "x": 0.5, "y": 0.5 }
      // { "type": "arrow", "from": [0.1,0.2], "to": [0.3,0.25] }    // 箭头：从 from 指向 to
      // { "type": "path", "points": [[0.1,0.2],[0.15,0.22], …] }   // 手绘圈画
      // { "type": "path", "points": [ … ], "breaks": [12] }        // 断成几段的一笔：从 points[12] 起是新的一段，和前一个点不连线
      // 每一处都可以带 "color": "#ffc233"：这一处单独换的颜色（可选），见下
    ]
  },
  "snapshot": "snapshots/k3f9a2.png",   // 相对 .sniptoss/
  "author": "user",
  "created_at": "2026-10-13T10:20:00Z",
  "updated_at": "2026-10-13T10:20:00Z",
  "handed_off_at": "2026-10-13T10:32:00Z",  // 可选：最近一次复制出去（复制成文字、复制成图片）的时间；没复制过就没有
  "material_sha256": "9f2c…",           // 可选：写这条批注时素材的 SHA-256；和素材现在的不一样 = 这条写在旧版本上，见下
  "color": "#5b8cff",                   // 可选：这条的标记单独换的颜色 #rrggbb；没有 = 用设置里的标记颜色，见下
  "replies": [                          // agent 改完回一句，或提问
    { "author": "codex", "body": "已换成思源黑体 Bold", "at": "2026-10-13T11:02:00Z" }
  ]
}
```

为什么坐标用 0–1：素材缩放、换分辨率导出后位置仍然对得上。要像素时乘以 `width`/`height`
（`REVIEW.md` 里已经替 agent 算好了）。

界面画的点、框、箭头对齐到素材的整像素（手绘 `path` 除外），存成 4 位小数（边长 1 万像素起每多一位数多一位小数，
x 看 `width`、y 看 `height`）；乘回 `width`/`height` 后四舍五入就是界面上显示的那个整数像素。

可以从画面外起笔，但只记画面里的部分：框取和画面重叠的那块，箭头取画面里的那一截，
手绘裁掉画面外的部分（出去又回来就断成几段，见 `breaks`）。所以坐标总在 0–1 之内。

`shapes` 里有几项，这条意见就标了几处，**意见对每一处都适用**（「这三个按钮都改成圆角」：用户在界面上画了三个框、只写一句话；sniptoss/5 起，以前一条只能标一处）。
几处共用一个编号、一张截图（截图里每处都画出来）、同一个时间（视频）、同一页（PDF）。顺序是用户画的先后，没有别的含义。

`shapes` 省略 = 针对整张图 / 整页 / 整个时间段的意见。视频上有 `anchor.time`、没有 `shapes` 的，界面叫「时间点意见」（针对那一刻或那一段的整个画面）；`time`、`shapes` 都没有的叫「整体意见」（针对整个视频）。只是界面上的分类，格式是同一个。

`handed_off_at`（可选字段）：界面每次复制出去时记下，批注栏据此标「已复制 · 10:32」。
它不算对批注的修改，所以不动 `updated_at`；两边同时改了取较晚的那个。旧程序读到会原样保留。

`color`（可选字段）：用户给这条的标记单独换的颜色，`#` 加 6 位十六进制。
没有这个字段 = 跟着设置里的「标记颜色」走；用户换回设置里的那个颜色时程序去掉这个字段。旧程序读到会原样保留（照设置的颜色画）。

`anchor.shapes` 里每一处的 `color`（可选字段）：标了几处的批注，用户可以给某一处单独换颜色，
好在意见里按颜色说哪处怎么改（「橙色那处改成圆角，黄色那处去掉」）。每一处画成它自己的 `color`，没有就用这条的 `color`，再没有就用设置里的标记颜色。
超级批注写的文件里：几处颜色不一样时**每一处都带 `color`**（不知道用户设置的程序也说得出每处是什么颜色），这条的 `color` 是第一处的颜色（旧程序照它画整条）；
几处又一样了就去掉每处的、只留这条的；给整条换颜色时去掉每处的。只有一处的批注不写每处的颜色。

颜色只管画面上、截图里、「复制成图片」里画成什么颜色，和意见内容本身无关。但用户会在意见里按颜色指某一处，
所以**几处颜色不一样时，REVIEW.md 和「复制成文字」在每处前面写上颜色**（「2 处：（橙色）位置 …；（黄色）位置 …」，预设的六种说名字，别的写色值）；颜色都一样时不提颜色。

### 写在旧版本上的批注（`material_sha256`，可选字段）

素材可能被原地覆盖（AI 改完存回同一个文件）。这时旧批注的位置对的是覆盖前的画面，放到新画面上就错了。所以每条批注记下写它时素材的 SHA-256（十六进制小写），
**和素材现在的指纹不一样 = 这条写在旧版本上**：位置、时间对应当时的画面，以它的截图为准（截图存的是当时的整张画面 + 标记）。

- 超级批注新写的批注都带它（指纹算不出来时没有）；改文字、改状态不动它。
- 没有它的批注（比如别的程序写的）：`created_at` 晚于素材文件的修改时间 = 写它之后素材没改过，就是现在这一版；早于的按文件的 `material.sha256` 算。
  规则在 core 的 `versions.ts`（`writtenOn`、`earlierVersions`），界面和命令行共用。
- 超级批注不在画面上画旧版本上的批注，批注栏里单独列成一节；复制成文字时单独一节、说明以截图为准；`REVIEW.md` 和 `sniptoss list` 每条后面注明。
  批注本身不改、不删，状态由用户管（docs/adr/0008-earlier-versions.md）。

## `REVIEW.md` 长什么样

只列 `open` 的批注，按素材分组，每条一段，**agent 不需要解析 JSON 就能动手**。整个文件夹的意见排在最前（先说整体、再说每个文件）。
写在旧版本上的批注（见上）在那一行末尾注明「（写在旧版本上，位置以截图为准）」。
标了几处的（`shapes` 不止一项）写成「2 处：……；……」，开头的说明里多一句「标了几处的批注，意见对每一处都适用」（只在有这种批注时写）；几处颜色不一样时每处前面写颜色（见上）。
有读不了的批注文件（见「读取规则」）时，标题下面先列出是哪几份、为什么，里面的批注不算进条数：

```markdown
# 待处理批注（3 条）

以下是用户使用超级批注（SnipToss）为素材添加的批注。请逐条处理：查看「截图」确认位置（截图中已画出标记），再按批注修改对应素材。
标为「整个文件夹」的批注适用于该文件夹内的全部素材（含子文件夹；./ 指 .sniptoss 所在的文件夹本身），而非其中某一个文件。
标了几处的批注，意见对每一处都适用。
文件和截图的路径均相对于项目文件夹（即 .sniptoss 所在的文件夹）。位置描述先给出画面中的大致方位，括号内为以左上角为原点的百分比；px 为素材原始像素，原点在左上角；视频时间格式为 分:秒.毫秒（一小时以上为 时:分:秒.毫秒）。

## ./  ·  文件夹意见，适用于文件夹内的全部素材（含子文件夹）

### [r0ot01] 修改 · 整个文件夹
所有图右下角统一加水印

## assets/hero.png  ·  图片 1920×1080

### [k3f9a2] 修改 · 2 处：区域 画面左上（横 12%–52%、纵 8%–18%），x=230 y=86 宽=768 高=108 px；区域 画面左下（横 12%–52%、纵 62%–72%），x=230 y=670 宽=768 高=108 px
标题字太细了，换成粗一点的黑体
截图：.sniptoss/snapshots/k3f9a2.png

## video/intro.mp4  ·  视频 1280×720 · 01:03.200

### [p0c7xe] 删除 · 00:12.500–00:15.000 · 位置 画面右下（横 90%、纵 90%），x=1152 y=648 px
这段水印去掉
截图：.sniptoss/snapshots/p0c7xe.png
```

## 读取规则（程序怎么读，写脚本、手改 JSON 时照这个来）

2026-10-17 起（docs/adr/0006-format-versioning.md）。超级批注和 `sniptoss` 命令读每个批注文件时：

- **不认识的字段原样保留**：文件、`material`、单条批注、`anchor` 上多出来的字段，程序改动后写回时都还在。自己的工具可以往里加东西。
- **旧写法照样认**：`anchor.shape`（一个形状，`sniptoss/4` 及以前）读成只有一项的 `shapes`，写回时是 `shapes`。
  `sniptoss/5` 的文件里写了 `shape`、没写 `shapes` 的（照旧文档手改的 JSON）也这样认；两个都写了的以 `shapes` 为准，`shape` 当不认识的字段留着。
- **可以省略、读时补上的**：`anchor`（当 `{}`）、`anchor.shapes` 是空数组时当没有（写回时去掉）、`replies`（当 `[]`）、`author` / `created_at` / `updated_at`（当空字符串）、回复里的 `author` / `at`（当空字符串）；`handed_off_at` 不是能解析的时间时当没有（写回时去掉）；`material_sha256` 不是字符串时当没有（写回时去掉）；`color`（这条的、每一处的）不是 `#rrggbb`（大小写都认）时当没有（写回时去掉）。
- **必须对的**（不对就整份文件读不了，见下）：`material.path`、`material.kind` 是非空字符串；`annotations` 是数组；
  每条批注的 `id` 非空且在本文件里不重复，`status` 是 `open | resolved | wontfix` 之一，`category` 是 `change | remove | add | question` 之一，`body` 是字符串；
  `anchor.page` 是 ≥ 1 的整数；`anchor.time.start`（和 `end`，有的话）是数字；回复的 `body` 是字符串；
  `anchor.shapes`（有的话）是数组，每一项是带 `type`（字符串）的对象；已知形状的坐标是有限的数字（`rect` 的 `x y w h`、`point` 的 `x y`、`arrow` 的 `from` / `to` 是 `[x, y]`、`path` 的 `points` 是 `[[x, y], …]`、`breaks` 是整数数组）。
  不认识的 `type` 不算错（以后加的形状），画的地方跳过。
- **读不了的文件不挡别的**：界面在批注栏顶上写明是哪个文件、为什么（不是合法 JSON / 不认识的格式 / 哪个字段不对），这份素材的批注先不能改——
  免得拿空白的去盖掉那份读不了的；文件修好或删掉后自动恢复。命令行跳过它，在标准错误里说一声，其余照常。
  `REVIEW.md` 顶上列出读不了的文件（agent 首先读它，不说的话会以为批注就这么多）。
- **比这一版新的格式**（`sniptoss/6` 起）：能读懂的照常显示，**只能看不能改**（界面提示升级，命令行的 `resolve` / `wontfix` 拒绝并说明）；读不懂的当读不了。
- `status`、`category` 加新的值、改坐标或时间的单位、改字段的结构（`sniptoss/5` 把 `shape` 改成 `shapes`）这类「旧程序会读错」的改动才升主版本号；只加可选字段不升。

每个版本的样例在 `tests/golden/formats/`，测试保证它们都能读、写回后内容不丢。

## agent 怎么处理批注

1. 读 `.sniptoss/REVIEW.md`；需要确认位置时打开对应截图。
2. 按批注修改素材。

不需要回写状态：修改后的素材由用户重新导入、核对，批注的状态由用户在超级批注中标记，原有批注保留作为记录。
命令行 `sniptoss resolve` / `wontfix` 仍然可用，供用户自己的脚本使用；直接修改 JSON 时，改 `status` 并在 `replies` 中追加一条，然后运行 `sniptoss review` 重新生成 `REVIEW.md`。

## 从 pizhu 迁移（2026-10-17）

超级批注的技术名从拼音 pizhu 改成了英文名 SnipToss（docs/adr/0007-rename.md），格式本身没变：

| 以前 | 现在 |
|---|---|
| 数据目录 `.pizhu/` | `.sniptoss/`（里面的结构、文件名都一样） |
| `"schema": "pizhu/1"`–`"pizhu/3"` | `"sniptoss/4"`（内容和 `pizhu/3` 一样；旧版本照常能读，程序写回时升到 `sniptoss/4`） |
| 回写脚本 `.pizhu\pizhu.cmd`、命令 `pizhu` | 命令 `sniptoss`（10-20 起不再往项目里放回写脚本，以前放的 `.sniptoss\sniptoss.cmd` 打开项目时删掉） |

- 超级批注**打开项目时**把 `.pizhu/` 整个改名成 `.sniptoss/`（改名不了就复制过去，旧的删得掉就删）；旧的 `pizhu.cmd` 删掉（10-20 起不再放新的回写脚本）。
- 命令行遇到还没被打开过、只有 `.pizhu/` 的项目，就在 `.pizhu/` 里原地读写，不另建 `.sniptoss/`。
- 自己写脚本读批注的：先找 `.sniptoss/`，没有再找 `.pizhu/`；`schema` 认 `pizhu/1`–`pizhu/3` 和 `sniptoss/4`。
- 改名前复制给 AI、还没处理的文字里写的是 `.pizhu\pizhu.cmd`，项目搬过来之后这个路径就没了，重新复制一次即可。
